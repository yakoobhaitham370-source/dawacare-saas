# Database

Apply migrations in lexicographic order to an empty Supabase development project first. They target the Supabase-provided `auth.users`, `auth.uid()`, `auth.jwt()`, `authenticated` role and `storage` schemas. Files are not destructive reset scripts and are not safe to run repeatedly against an already migrated database. For subsequent releases use a versioned migration ledger and inspected CLI workflow.

- `0001_core`: normalized platform/clinical/operational tables, composite tenant foreign keys, indexes, RLS, audit triggers, patient limits, append-only dispensing, atomic projection and task updates.
- `0002_invitations_and_safety`: MFA-gated platform access, pharmacy provisioning, seat reservations, verified invitation acceptance, payment confirmation, subscription transitions and immutable actor/context stamping.
- `0003_storage`: private bucket and metadata-based object read policy. No public upload/delete policies.
- `0004_ai`: serialized monthly/rate quota reservation and pharmacist-reviewed atomic treatment persistence.
- `0005_staff`: owner-only staff role/suspension management; no self/owner promotion.
- `0006_documents`: scoped registration, archive and access auditing. Netlify validates file magic, size, identity, membership and patient access before service-key upload; failed metadata registration requests object cleanup.

All tenant clinical reads require active membership and the retention window. Clinical writes require an eligible subscription. Platform admins have commercial metadata access only; they gain no clinical access without an independent pharmacy membership. Interactive service-role access is never a user role.

Dispensing supply is inclusive and generated by PostgreSQL as `dispensed_on + days_supply + carry_days - 1`. Projections use the latest actual dispensing date, not a backdated event's entry timestamp. Requests carry a UUID idempotency key; retrying the same event returns its original ID. Reminder uniqueness is enforced on `(pharmacy_id, dispensing_event_id)`. Creating the event, projection and task is a single transaction; no scheduler is required for these first projections. Periodic job orchestration and task reassignment are still pending.

Patients have tenant-scoped display numbers assigned while locking the pharmacy row. Archived records count toward the subscription patient limit so archival cannot bypass licensed storage limits. Clinical audit rows record actor, action and record ID, not full before/after medical contents. The fuller correction/revision UX and history model remain pending.

`npm run test:db` uses PGlite's actual PostgreSQL engine with non-owner `authenticated` sessions. The tests emulate Supabase auth functions and storage tables. They exercise RLS, constraints and privileged SQL functions; they do not exercise the real Supabase Auth, PostgREST, email or Storage services.

Migrations added by the integration branch (the original six are unchanged):

- `0007_integration_hardening`: explicit table/function ACLs compatible with Supabase default grants; immutable patient numbers; self-scoped notification preferences; AI job/usage tenant FK; payment currency check; server-only document registration.
- `0008_invitation_lifecycle`: delivery lease/cooldown/cap, authorized retry/revoke/renew, existing-user lookup limited to service-role execution, explicit verified invitation acceptance, current inviter and seat revalidation. Acceptance and preparation lock the pharmacy first to serialize reservations/activation.
- `0009_dispensing_replay_integrity`: compare every persisted clinical/reminder/correction field for an existing request ID. A changed carry-over decision is not a replay.

The new PGlite fixture deliberately grants broad Supabase-style default privileges before migration to test that the hardening revokes them. Original migration tests continue, and additional cases cover leases, multi-membership acceptance, expiration, revocation, seat reductions, stale delivery completion and API grant boundaries.

The local CLI configuration disables signup, enables TOTP and disables seed execution. It does not configure a hosted project. The optional real-service suite uses Auth/PostgREST/Storage plus a private development database connection and rejects unconfirmed remote test targets. It is separate from `npm test`.

No production patient seeds are supplied or run. The browser-only synthetic seed is wholly separate from Supabase.
